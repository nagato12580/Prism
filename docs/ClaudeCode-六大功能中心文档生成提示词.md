# Claude Code：六大功能中心文档生成提示词

> 使用方法：在项目根目录打开 Claude Code，将“提示词正文”下的内容完整复制并发送。该任务会沿用现有项目知识库，并按照六大功能中心生成端到端详细文档。

---

# 提示词正文

请继续完善当前项目的中文项目知识库。

当前项目已经生成了一批按照总体架构、技术实现和企业级质量属性组织的文档。现在需要在现有成果基础上，新增一套按照“系统功能中心”组织的详细文档。

本次不是简单重新分类、复制已有文档，也不是只为六个中心分别写一篇概述。你需要从业务功能和用户操作出发，对每个功能中心进行端到端调查，达到现有项目知识库相同甚至更细的分析粒度。

最终文档需要帮助一名零基础读者理解：每个功能中心解决什么业务问题、有哪些实际功能、用户如何使用、前后端如何实现、API 如何调用、数据如何流转和保存、依赖哪些内部模块和外部系统、正常和异常流程如何执行、熔断重试降级兜底如何实现，以及如何保障安全、性能、一致性、测试、监控、部署和排障。

不要担心 Token 消耗。完整性、准确性和可追溯性优先于速度。

## 一、六个功能中心

按照以下六个中心组织文档：

1. 库表知识中心
2. 文件知识中心
3. 工具接口中心
4. 本体推理中心
5. QPAI 引擎中心
6. 系统管理中心

这些名称是业务视角的初始分类，不代表代码一定以相同方式划分。必须通过页面、前端路由、API、后端服务、数据库、缓存、任务、搜索、图谱、模型调用、外部服务和测试，调查每个中心的真实边界。不得仅根据目录名、文件名、类名或注释猜测归属。

## 二、最高执行原则

1. 只分析和编写文档，不修改业务代码、数据库、依赖、运行环境和部署配置。
2. 只允许在 `docs/project-handbook/` 中创建或修改本任务相关文档。
3. 未经明确授权，不执行 Git commit、push、merge、rebase，不创建分支或 PR。
4. 不执行破坏性命令，不连接真实生产数据库、生产服务或付费第三方服务，不发送会改变数据的真实请求。
5. 不记录真实密码、Token、Cookie、私钥、Access Key、Secret、连接密码或个人隐私。敏感配置只记录名称、用途、来源、必填性和脱敏格式。
6. 不大段复制源码。可以引用必要的类名、函数名、路由、字段和配置名，重点解释实现机制、调用链、数据流、业务规则与关键参数。
7. 每个重要结论必须有代码、配置、测试、历史记录或项目文档证据。
8. 不得把常见实践、框架默认能力或理论可能性写成项目已经实现的事实。
9. 找不到证据时写“未发现实现证据”；只能由运行环境证明时写“运行时待验证”；需要询问人员时写“人员待确认”。
10. 如果代码、配置、测试、旧文档和提交历史冲突，记录冲突，不得自行选定结论。
11. 面向零基础读者写作，术语首次出现时通俗解释，先讲为什么，再讲如何实现。
12. 文档必须脱离当前对话独立阅读，适合长期离线保存。

## 四、Subagent 执行方式

本任务预计超过单个上下文窗口，必须采用“主 Claude 协调和整合 + 多个 subagent 分模块调查 + 分批生成 + 最终审计”。

主 Claude 负责读取现有成果、确定边界、拆分任务、管理进度、审核研究结果、处理跨中心关系、整合正式文档、维护公共导览和矩阵、检查矛盾及执行覆盖率审计。

Subagent 负责调查被分配的有限范围，阅读源码、配置、测试和旧文档，形成结构化研究报告并标注证据与不确定性，不修改业务代码。

执行规则：

1. 优先并行处理互不依赖的调查任务。
2. 每个 subagent 范围必须明确、有限且互不冲突，不得让单个 agent “分析整个项目”。
3. 不允许多个 agent 同时编辑同一文件。
4. Subagent 不得编辑公共导览、索引、进度和覆盖率文件。
5. Subagent 研究结果写入唯一文件：`docs/project-handbook/_research/function-centers/<任务编号>-<主题>.md`。
6. 正式文档由主 Claude统一整合。
7. 一个中心过大时，继续按业务子功能拆分。
8. 共享模块只记录依赖，不重复认定为多个中心私有。
9. 跨中心问题建立专门调查任务。
10. “未发现实现”必须写清搜索过的目录、关键词和配置范围。
11. 环境不支持 subagent 时，按相同任务划分串行执行，不得缩减范围。

每个 subagent 的报告至少包含：调查范围、排除范围、功能清单、用户角色、页面和操作、前端入口、API、后端调用链、数据实体和数据流、状态变化、缓存消息任务、外部依赖、关键参数、正常和异常流程、超时重试熔断兜底、安全权限、性能容量成本、日志监控排障、测试证据、风险技术债、未确认问题及证据文件列表。

## 六、证据标签

沿用以下标签：

- 【代码事实】：实际业务代码直接证明。
- 【配置事实】：配置文件证明，但未必是生产真实值。
- 【测试事实】：测试证明预期行为，但不保证生产链路已启用。
- 【文档声明】：旧文档如此描述，尚未完全由代码验证。
- 【历史证据】：Git 或设计记录证明。
- 【合理推断】：多个证据推导，仍需确认。
- 【运行时待验证】：必须启动系统或查看运行数据才能确认。
- 【人员待确认】：需要询问产品、开发、测试、运维、安全或业务人员。
- 【未发现实现】：搜索相关范围后没有找到实现。

重要结论至少标注证据类型、仓库相对路径、关键类/函数/路由/配置/模型/测试名称、可信度和是否需要进一步验证。

## 八、总导览页面

`function-centers/README.md` 必须包含：六个中心的一句话介绍、功能视角的用途、与原技术视角文档的关系、真实边界、中心依赖图、公共能力、推荐阅读顺序、按学习目标划分的阅读路线、每篇文档介绍、完成度、高风险和未确认信息、可信度说明，以及如何从功能追踪代码和从代码反查业务。

每篇文档注明用途、适用场景、前置知识、阅读难度、完成状态和更新时间。

## 九、正式写作前先确定真实边界

先调查每个中心对应的菜单、页面、路由、组件、API、Controller/Router/Handler、Service、Repository/Client、数据库表/集合/索引/图结构、缓存、消息、任务、文件存储、搜索、向量、图谱、模型、外部系统、配置和测试。

同时识别：共享模块、无法归属功能、无调用入口代码、仅存在旧文档的功能、存在代码但无页面入口的能力，以及业务结构与代码结构的差异。

公共模块必须标记为公共基础能力、主要所属中心、次要使用中心、跨中心编排能力或待确认归属。记录业务边界、代码边界、映射、耦合、维护风险和待确认问题。

## 十、每个中心的统一分析粒度

### 1. 中心导览

包含业务价值、目标用户、边界、不属于本中心的功能、子功能、页面、API、数据实体、系统组成、上下游、公共依赖、阅读顺序、文档介绍、完成度、高风险和未知信息。

### 2. 业务与用户

说明业务问题、场景、角色、输入输出、核心对象、业务规则、状态和生命周期、页面路由、操作步骤、表单、加载/空/成功/失败/无权限状态、前端状态管理，以及页面到 API 的映射。

### 3. 架构与模块

说明前端、后端、数据访问、任务、公共基础、缓存消息、搜索图谱模型、外部依赖的职责、调用关系、边界、上下游、可替换组件、耦合和风险。

### 4. 每项核心功能

每项用户可感知功能必须回答：名称、业务目的、角色、入口、前置条件、规则、操作步骤、前端实现和请求、后端入口和完整调用链、参数与权限校验、业务处理、数据转换和读写、状态变化、缓存、消息任务、搜索向量图谱、模型/Agent、外部调用、事务、成功和异常结果、超时重试回滚补偿熔断兜底、幂等、关键参数、测试、日志监控、证据、风险和待确认问题。

### 5. API 和调用链

每个 API 说明方法、路径、用途、调用方、认证权限、路径/查询/请求体参数、类型、必填、默认值、限制、返回结构、HTTP 状态、业务错误码、后端入口、服务调用、数据影响、任务和外部调用、幂等、事务、超时、重试、熔断、限流、测试和证据。

建立：用户操作 → 页面 → 前端事件/请求 → API → Controller/Router → Service → Repository/Client/Task → 数据库/缓存/消息/搜索/图谱/模型/外部服务 → 返回 → 页面状态 → 用户结果。

### 6. 数据模型与数据流

说明实体含义、字段、主外键和关系、状态机、生命周期、CRUD/归档入口、约束和索引、校验转换、来源和权威源、存储、缓存、搜索/向量/图谱/文件/临时数据、同步、一致性、隔离、保留、清理、迁移和恢复。使用必要的 ER 图、数据流图和状态机图。

### 7. 配置参数

列出名称、默认值、单位、定义/读取/使用位置、环境覆盖、是否需重启、影响、过大过小后果、敏感性、硬编码、测试情况和生产值是否可确认。重点关注超时、重试、熔断、并发、连接池、线程池、队列、批量、分页、文件大小、缓存时间、Token、模型、搜索/重排数、Agent 最大步骤、功能开关和日志级别。

### 8. 安全权限与隔离

调查认证、角色、菜单/页面/按钮/API/数据权限、租户组织隔离、输入输出校验、文件安全、SQL 注入、XSS、CSRF、SSRF、命令注入、敏感数据、加密脱敏、审计、管理员操作、越权串租、外部认证，以及安全依赖故障时默认放行还是拒绝。

### 9. 稳定性、熔断、重试与兜底

调查各层超时、重试次数与间隔、指数退避、随机抖动、可重试异常、熔断失败率/最小请求/窗口/持续时间/半开/恢复、降级、缓存或默认结果、备用服务/模型、限流、排队、背压、并发限制、线程池/连接池隔离、舱壁、事务回滚补偿、幂等、重复请求/消费、优雅关闭、健康检查、自动重启和数据恢复。

每种机制必须回答：是否真实实现、保护什么、位置、触发条件、参数和单位、过程、用户表现、数据风险、传播路径、恢复条件、监控、测试、薄弱点、改进建议和证据。不得把框架能力写成已启用能力。

### 10. 并发与一致性

调查重复提交、多用户并发、多实例竞争、乐观/悲观/分布式锁、锁超时、死锁、事务边界和隔离级别、竞态、覆盖、幂等键、重复消息、最终一致性、补偿、部分成功和数据修复。

### 11. 性能容量成本

分析请求并发、查询复杂度、数据/批处理规模、分页索引缓存、连接/线程池、队列、文件、CPU/内存/网络、搜索向量图计算、模型和外部调用延迟、存储网络搜索和 Token 成本、调用放大、配额、瓶颈、扩展、容量上限和压测缺口。生产规模不能证明时明确待确认。

### 12. 日志监控排障

说明日志位置格式级别、Trace/Request/用户/任务标识、指标、健康检查、链路追踪、告警、错误码、定位入口、排障步骤、恢复验证，以及缺失的可观测性。

### 13. 测试

建立“功能 → 测试文件 → 类型 → 正常路径 → 异常路径 → 稳定性场景 → 缺口”映射，覆盖单元、集成、API、前端、端到端、数据库、任务、性能、安全、故障演练、Mock、测试数据和运行方法。

### 14. 风险和学习

分别记录已确认问题、潜在风险、缺失机制/测试、TODO/FIXME、硬编码、配置/安全/性能/成本/一致性风险、单点、文档冲突、业务和生产未知项、应询问角色和优先级。事实与建议分开。为零基础读者提供前置知识、术语、文档和源码阅读顺序、追踪示例、常见误区、分级自测题及答案。

## 十一、各中心专项重点

### 库表知识中心

调查数据源和凭证、连接测试、库/Schema/表/字段、元数据采集同步、数据预览、字段语义、主外键、资产目录标签、权限隔离、抽取清洗、向量/搜索/图谱、查询问答、增量更新删除、大表敏感表、连接和同步失败、凭证安全、一致性。

### 文件知识中心

调查上传、格式类型大小和安全校验、重复文件、存储命名元数据、解析/OCR/文本表格图片提取、清洗分块父子块页码、向量索引图谱抽取、搜索引用、版本重处理删除清理、后台任务和进度、大文件、存储/解析/模型故障及重试兜底。

### 工具接口中心

调查工具定义注册发现目录、参数 Schema、HTTP/MCP/插件/内部工具、认证权限校验、调用和返回、日志审计、超时重试熔断限流幂等、失败处理、版本和上下线、测试、SSRF/命令注入/泄露、付费调用，以及工具结果如何进入 QPAI/Agent。

### 本体推理中心

调查本体、类型、实体关系属性规则和 Schema、创建编辑版本、实体关系抽取与消歧合并、图谱构建查询扩展、路径和社区、规则/模型推理、推理链证据可信度、冲突、增量删除回滚、图存储、规模性能、错误推理和幻觉，以及如何向 QPAI 提供结果。

### QPAI 引擎中心

先从代码和文档确认 QPAI 的准确含义，不得自行展开缩写。调查定位、入口调度、Agent、Prompt、模型、工具、意图和查询理解/改写、规划、RAG、关键词/向量/图/混合检索、重排、上下文和 Token、推理生成流式输出、引用证据、会话记忆、模型路由和备用、超时重试熔断降级、循环和最大步骤、工具失败、幻觉和内容安全、评测、性能成本，以及与其他中心的关系。

### 系统管理中心

调查用户组织部门租户、角色权限菜单按钮数据权限、登录 Token Session 密码 SSO、认证失败和权限变更、配置字典功能开关、模型和外部服务配置、任务日志审计告警状态、备份恢复清理、管理员危险操作、多租户、密钥和运维入口，以及如何支撑其他中心。

## 十二、跨中心文档

`00-六大功能中心全景.md`：业务定位、边界、角色、输入输出、关系、全景图、公共能力、重叠争议、推荐顺序和代码映射。

## 十三、写作和图表规范

每篇文档尽量包含：目标、读者、前置知识、通俗解释、真实实现、组件、输入处理输出、正常和异常流程、数据和状态、参数、跨中心关系、安全性能稳定性、测试证据、风险、未知项、小结和自测题。

使用简体中文。参数写实际默认值和单位，解释影响；事实与建议、设计与实现、开发默认与生产事实分开。引用仓库相对路径，维护文档链接，避免重复矛盾。

必要时使用 Mermaid 生成中心全景、上下文、模块依赖、页面到后端调用、流程、时序、数据流、ER、状态机、异步任务、故障传播和恢复图。图表必须符合证据，未知节点标记待确认。

## 十四、执行阶段

### 阶段 1：读取规则和现有成果

读取项目规则、知识库、进度、覆盖矩阵和冲突，区分已确认事实和需要复核内容。

### 阶段 2：建立真实映射

扫描页面、路由、API、服务、数据、任务、外部依赖、配置和测试，建立中心归属、共享模块、跨中心链路和边界冲突。先创建全部 `_meta` 文件，不要凭名称直接写正式文档。

### 阶段 3：制定 Subagent 计划

根据规模确定中心范围、子功能、agent 任务、跨中心任务、批次和依赖。向我简要报告初步边界、公共模块、subagent 计划、批次、未知项和上下文风险，然后继续执行；仅在权限、安全或范围冲突时暂停。

### 阶段 4：逐中心调查

顺序依据真实依赖。如果没有更合理证据，可参考：系统管理 → 库表知识 → 文件知识 → 本体推理 → 工具接口 → QPAI → 跨中心。

### 阶段 5：逐中心生成

每完成一个中心，检查功能、页面、API、服务、数据、配置、正常异常流程、稳定性、安全、性能成本、日志排障、测试、证据和旧文档冲突，并更新导览、进度和覆盖率。

### 阶段 6：跨中心整合

生成全景、业务流程、数据流、权限矩阵、故障矩阵和配置索引。

### 阶段 7：最终审计

检查所有用户功能、页面、路由、API、服务、数据实体、任务、外部依赖、配置和测试是否归属；检查重复统计、无人归属、仅页面无后端、仅代码无入口、旧文档与当前代码冲突；检查异常、稳定性、安全隔离、并发一致性、性能成本、事实标签、敏感信息、Mermaid 和链接。

将结果写入 `docs/project-handbook/function-centers/06-功能中心覆盖率与审计报告.md`，并同步全局进度和覆盖矩阵。

## 十五、完成标准

只有满足以下条件才算完成：

1. 六个中心都有导览、完整子功能和推荐阅读顺序。
2. 每项重要功能可追踪到页面、API、服务、数据、任务、依赖和测试。
3. 每个中心都有业务规则、前后端实现、数据模型、流程和关键参数。
4. 每个中心都有异常、熔断重试降级兜底、并发事务幂等、安全隔离、性能成本、日志排障和测试缺口分析。
5. 跨中心调用、数据流、公共能力和私有能力已经说明。
6. 权限矩阵、故障矩阵、配置索引和最终审计已经完成。
7. 未实现机制明确指出，未知信息进入待确认和访谈清单。
8. 所有重要结论可追溯，文档适合零基础人员独立学习。
9. 没有修改业务代码，没有泄露敏感信息。
