- # 微调大模型完整指南

  ## 一、微调大模型到底是在做什么

  微调大模型，本质上是让一个已经具备通用语言能力的预训练模型，进一步适应你的具体业务任务、数据分布和输出格式。

  常见微调目标可以分为两类：

  ### 1. 分类类任务

  例如：

  - 情感分类：正面 / 负面 / 中性
  - 意图识别：咨询价格 / 投诉 / 售后 / 其他
  - 风险识别：正常 / 涉政 / 色情 / 诈骗 / 暴力
  - 工单分类：退款 / 物流 / 账号 / 技术问题

  这类任务通常有明确标签，训练数据格式类似：

  ```json
  {
    "text": "这个订单为什么还没发货？",
    "label": "物流问题"
  }
  ```

  ### 2. 生成类任务 / 指令微调任务

  例如：

  - 客服问答
  - 文案生成
  - 总结改写
  - 代码生成
  - 多轮对话
  - 结构化信息抽取

  这类任务通常训练模型学会根据 instruction / input 生成 output，数据格式类似：

  ```json
  {
    "instruction": "请判断下面用户问题的意图",
    "input": "我的快递三天没动了",
    "output": "物流问题"
  }
  ```

  或者：

  ```json
  {
    "messages": [
      {"role": "user", "content": "帮我写一段商品介绍"},
      {"role": "assistant", "content": "这款商品采用轻量化设计，适合日常通勤使用。"}
    ]
  }
  ```

  ------

  ## 二、微调大模型的完整流程

  完整流程可以分为四个核心阶段：

  1. 数据理解
  2. 跑通训练
  3. 评估复盘
  4. 推理落地

  其中最容易被新手忽略的是：**微调不是先调参数，而是先把数据、标签、评估和推理闭环跑通。**

  ------

  # 第一阶段：数据理解

  ## 1. 明确任务定义

  在开始训练前，必须先回答四个问题：

  ### 问题一：模型输入是什么？

  例如：

  - 单句文本
  - 多轮对话
  - 标题 + 正文
  - 用户问题 + 商品信息
  - 用户问题 + 检索结果
  - prompt + instruction

  错误示例：

  ```text
  输入字段随便拼，今天用 title，明天用 content。
  ```

  正确做法：

  ```text
  明确模型最终线上会看到什么，训练输入就尽量模拟什么。
  ```

  ------

  ### 问题二：模型输出是什么？

  分类任务输出通常是标签：

  ```text
  物流问题、退款问题、账号问题、其他
  ```

  生成任务输出通常是自然语言、JSON 或固定格式文本：

  ```json
  {
    "意图": "退款问题",
    "情绪": "负面",
    "是否需要人工": true
  }
  ```

  ------

  ### 问题三：标签从哪里来？

  标签必须来自真实标签列，不能从输入字段复制。

  错误示例：

  ```python
  labels = data["text"]
  ```

  正确示例：

  ```python
  labels = data["label"]
  ```

  对于分类任务，标签列应该是人工标注、业务系统记录或经过审核的真实结果。

  ------

  ### 问题四：成功标准是什么？

  不要只说“模型效果变好”，要提前定义可量化标准。

  例如：

  ```text
  目标：
  - 验证集 Macro F1 ≥ 0.82
  - 退款类 Recall ≥ 0.90
  - 典型人工测试样本 30 条中至少 26 条预测正确
  - 线上灰度后误判率低于旧模型
  ```

  ------

  ## 2. 检查数据质量

  微调效果的上限，往往由数据质量决定，而不是由参数决定。

  ### 必查项目

  | 检查项   | 说明                                 |
  | -------- | ------------------------------------ |
  | 缺失值   | text 或 label 为空的样本应删除或修复 |
  | 重复样本 | 大量重复会导致模型记忆训练集         |
  | 标签错误 | 错标会严重污染模型                   |
  | 标签分布 | 判断是否类别不平衡                   |
  | 文本长度 | 决定 max_length 设置                 |
  | 脏数据   | HTML、乱码、异常符号、广告文本等     |
  | 泄漏字段 | 输入中不能包含答案或标签信息         |

  ------

  ## 3. 标签体系设计

  标签体系必须满足三个要求：

  ### 1. 互斥

  分类任务中，一个样本最好只能属于一个主标签。

  错误示例：

  ```text
  退款、售后、订单问题
  ```

  这三个标签边界不清，容易混淆。

  正确示例：

  ```text
  仅退款、退货退款、物流异常、账号问题、其他
  ```

  ------

  ### 2. 可解释

  每个标签都要有定义、正例和反例。

  示例：

  ```text
  标签：物流异常
  
  定义：
  用户询问发货、运输、快递、配送、签收异常等问题。
  
  正例：
  - 我的快递为什么还没到？
  - 物流三天没更新了。
  - 显示签收但我没收到。
  
  反例：
  - 我要退款。
  - 商品质量不好。
  ```

  ------

  ### 3. 数量适中

  新手不建议一开始设计过多标签。

  建议：

  ```text
  初版标签数量：3–20 个
  复杂任务：先粗分类，再细分类
  ```

  ------

  ## 4. 划分训练集、验证集和测试集

  必须严格区分：

  | 数据集            | 用途                        |
  | ----------------- | --------------------------- |
  | 训练集 train      | 用来更新模型参数            |
  | 验证集 validation | 用来调参、选最佳 checkpoint |
  | 测试集 test       | 最终验收，不参与调参        |

  常见比例：

  ```text
  训练集：80%
  验证集：10%
  测试集：10%
  ```

  数据较少时：

  ```text
  训练集：80%
  验证集：20%
  ```

  ### 关键原则

  训练集和验证集必须严格分开，不能重复。

  错误做法：

  ```text
  同一条样本同时出现在 train 和 validation。
  ```

  后果：

  ```text
  验证指标虚高，上线效果明显下降。
  ```

  推荐做法：

  ```text
  按用户 ID、会话 ID、订单 ID 或时间切分，防止相似样本泄漏。
  ```

  ------

  # 第二阶段：跑通训练

  ## 1. 标准训练流程

  微调流程可以拆成 8 步：

  1. 定义标签映射
  2. 加载 tokenizer 和模型
  3. 读取数据并 tokenize
  4. 正确设置 labels
  5. 配置 LoRA 或全量微调参数
  6. 配置训练参数
  7. 训练并保存最佳模型
  8. 在验证集和测试集评估，并做推理验收

  ------

  ## 2. 分类任务数据格式

  推荐 CSV 或 JSONL。

  CSV 示例：

  ```csv
  text,label
  "我的快递为什么还没到？","物流问题"
  "我要申请退款","退款问题"
  "账号登录不上","账号问题"
  ```

  JSONL 示例：

  ```json
  {"text": "我的快递为什么还没到？", "label": "物流问题"}
  {"text": "我要申请退款", "label": "退款问题"}
  {"text": "账号登录不上", "label": "账号问题"}
  ```

  ------

  ## 3. 指令微调数据格式

  推荐使用 instruction / input / output 或 messages 格式。

  ### 单轮格式

  ```json
  {
    "instruction": "请判断用户问题的类别",
    "input": "我的快递为什么还没到？",
    "output": "物流问题"
  }
  ```

  ### 对话格式

  ```json
  {
    "messages": [
      {"role": "system", "content": "你是一个客服意图识别助手。"},
      {"role": "user", "content": "我的快递为什么还没到？"},
      {"role": "assistant", "content": "物流问题"}
    ]
  }
  ```

  ------

  ## 4. 定义标签映射

  分类任务必须建立 label 与 id 的映射。

  ```python
  label2id = {
      "物流问题": 0,
      "退款问题": 1,
      "账号问题": 2,
      "其他": 3
  }
  
  id2label = {
      0: "物流问题",
      1: "退款问题",
      2: "账号问题",
      3: "其他"
  }
  ```

  注意：

  ```text
  训练、验证、测试、推理必须使用同一份 label2id / id2label。
  ```

  ------

  ## 5. 加载 tokenizer 和模型

  分类任务通常使用：

  ```python
  AutoTokenizer
  AutoModelForSequenceClassification
  ```

  生成任务通常使用：

  ```python
  AutoTokenizer
  AutoModelForCausalLM
  ```

  如果是分类任务：

  ```python
  model = AutoModelForSequenceClassification.from_pretrained(
      model_name,
      num_labels=len(label2id),
      id2label=id2label,
      label2id=label2id,
      torch_dtype="auto"
  )
  ```

  如果是生成任务：

  ```python
  model = AutoModelForCausalLM.from_pretrained(
      model_name,
      torch_dtype="auto",
      device_map="auto"
  )
  ```

  ------

  ## 6. Tokenize 数据

  分类任务示例：

  ```python
  def tokenize_function(example):
      return tokenizer(
          example["text"],
          truncation=True,
          padding="max_length",
          max_length=256
      )
  ```

  指令微调示例：

  ```python
  def build_prompt(example):
      return f"""### 指令
  {example["instruction"]}
  
  ### 输入
  {example["input"]}
  
  ### 回答
  {example["output"]}"""
  ```

  ------

  ## 7. 正确设置 labels

  分类任务：

  ```python
  encoded["labels"] = label2id[example["label"]]
  ```

  生成任务：

  ```text
  labels 通常是 input_ids 的副本，但需要把不希望模型学习的 prompt 部分 mask 掉。
  ```

  核心原则：

  ```text
  模型只应该学习 assistant / output 部分，而不是盲目学习整段 prompt。
  ```

  ------

  # 第三阶段：训练配置

  ## 1. 全量微调、LoRA 和 QLoRA 的区别

  | 方式     | 说明                    | 优点           | 缺点                        |
  | -------- | ----------------------- | -------------- | --------------------------- |
  | 全量微调 | 更新模型全部参数        | 效果潜力高     | 显存和成本高                |
  | LoRA     | 只训练少量低秩适配参数  | 成本低、速度快 | 需要选择合适 target_modules |
  | QLoRA    | 量化加载模型，再做 LoRA | 显存占用更低   | 配置更复杂，速度可能受影响  |

  新手建议：

  ```text
  优先使用 LoRA。
  显存非常紧张时再考虑 QLoRA。
  数据量很大且资源充足时再考虑全量微调。
  ```

  ------

  ## 2. LoRA 常用参数

  | 参数           | 含义             | 新手起点             |
  | -------------- | ---------------- | -------------------- |
  | r              | 低秩矩阵维度     | 8 或 16              |
  | lora_alpha     | LoRA 缩放系数    | 16 或 32             |
  | lora_dropout   | dropout 概率     | 0.05                 |
  | target_modules | 注入 LoRA 的模块 | q_proj、v_proj 等    |
  | bias           | 是否训练 bias    | none                 |
  | task_type      | 任务类型         | CAUSAL_LM 或 SEQ_CLS |

  示例：

  ```python
  lora_config = LoraConfig(
      r=8,
      lora_alpha=16,
      lora_dropout=0.05,
      target_modules=["q_proj", "v_proj"],
      bias="none",
      task_type="CAUSAL_LM"
  )
  ```

  分类任务可以使用：

  ```python
  task_type="SEQ_CLS"
  ```

  ------

  ## 3. 训练参数建议

  | 参数                        | 新手起点       | 说明                  |
  | --------------------------- | -------------- | --------------------- |
  | learning_rate               | 5e-5           | LoRA 分类任务常用起点 |
  | epochs                      | 3–5            | 数据少时不要太多      |
  | batch_size                  | 按显存设置     | 先从 1、2、4、8 试    |
  | gradient_accumulation_steps | 4 或 8         | 显存不足时增大        |
  | max_length                  | 128–512        | 根据文本长度决定      |
  | weight_decay                | 0.01           | 防止过拟合            |
  | warmup_ratio                | 0.03–0.1       | 训练更稳定            |
  | logging_steps               | 10–50          | 方便观察训练          |
  | eval_strategy               | steps 或 epoch | 定期验证              |
  | save_strategy               | steps 或 epoch | 保存 checkpoint       |
  | load_best_model_at_end      | True           | 训练结束加载最佳模型  |

  ------

  ## 4. 调参顺序

  不要一开始乱调参数。推荐顺序：

  ### 第一步：先稳训练

  目标：

  ```text
  训练能正常跑完，loss 能下降，没有 NaN，没有显存爆掉。
  ```

  优先检查：

  ```text
  数据格式、labels、学习率、batch size、max_length。
  ```

  ------

  ### 第二步：再防过拟合

  如果训练集效果高、验证集效果低，说明可能过拟合。

  处理方式：

  ```text
  - 减少 epoch
  - 增加 dropout
  - 增加 weight_decay
  - 扩充数据
  - 清洗重复样本
  - 使用 early stopping
  ```

  ------

  ### 第三步：最后细调

  在流程稳定后，再细调：

  ```text
  - learning_rate
  - lora_r
  - lora_alpha
  - target_modules
  - max_length
  - prompt 模板
  ```

  ------

  # 第四阶段：评估复盘

  ## 1. Loss 不是最终效果

  Loss 是训练优化指标，表示模型在训练目标上的误差。

  但业务评估不能只看 Loss。

  常见情况：

  ```text
  Loss 下降，但 F1 不提升。
  Accuracy 很高，但少数类完全识别不出来。
  验证集指标很好，但线上样本效果差。
  ```

  所以需要组合评估。

  ------

  ## 2. 分类任务常用指标

  | 指标             | 含义                             |
  | ---------------- | -------------------------------- |
  | Accuracy         | 总体预测正确比例                 |
  | Precision        | 预测为某类的样本中，有多少是真的 |
  | Recall           | 某类真实样本中，有多少被找出来   |
  | F1 Score         | Precision 和 Recall 的综合       |
  | Macro F1         | 各类别 F1 的平均，适合类别不平衡 |
  | Weighted F1      | 按类别样本数加权的 F1            |
  | Confusion Matrix | 看模型把哪些类别混淆了           |

  ------

  ## 3. 不同任务看不同指标

  ### 类别均衡任务

  可以关注：

  ```text
  Accuracy + Macro F1
  ```

  ### 类别不平衡任务

  更关注：

  ```text
  Macro F1 + 每个类别的 Recall
  ```

  ### 风控、审核、召回类任务

  更关注：

  ```text
  Recall
  ```

  因为漏掉风险样本代价高。

  ### 误杀代价高的任务

  更关注：

  ```text
  Precision
  ```

  因为错判正常样本为异常会影响用户体验。

  ------

  ## 4. 混淆矩阵分析

  评估时一定要看混淆矩阵。

  示例：

  | 真实 \ 预测 | 物流 | 退款 | 账号 |
  | ----------- | ---- | ---- | ---- |
  | 物流        | 90   | 5    | 5    |
  | 退款        | 12   | 80   | 8    |
  | 账号        | 3    | 4    | 93   |

  从混淆矩阵可以看出：

  ```text
  退款问题经常被模型预测成物流问题。
  ```

  接下来应该回到数据中检查：

  ```text
  - 退款和物流标签定义是否重叠
  - 是否存在错标
  - 是否需要增加区分性样本
  - 是否需要优化 prompt 或输入字段
  ```

  ------

  ## 5. 建立基线

  不要只看微调后的绝对指标，要和基线比较。

  常见基线：

  ```text
  - 原始大模型 zero-shot
  - 原始大模型 few-shot
  - 传统机器学习模型，如 TF-IDF + LR
  - 旧线上模型
  - 人工规则系统
  ```

  成功不是“模型训练完了”，而是：

  ```text
  微调模型稳定超过基线。
  ```

  ------

  # 第五阶段：推理落地

  ## 1. 单条预测

  分类任务推理流程：

  ```text
  输入文本
  → tokenizer
  → model
  → logits
  → softmax
  → 取最大概率类别
  → id2label 转回标签
  ```

  示例输出：

  ```json
  {
    "text": "我的快递为什么还没到？",
    "pred_label": "物流问题",
    "confidence": 0.93
  }
  ```

  ------

  ## 2. 批量预测

  批量预测要注意：

  ```text
  - 使用 batch 推理提高吞吐
  - 设置 max_length
  - 避免一次性加载过大文件
  - 保存预测标签、概率、原始文本
  - 保留低置信度样本供人工复核
  ```

  推荐输出格式：

  ```csv
  text,pred_label,confidence
  "我的快递为什么还没到？","物流问题",0.93
  "我要退款","退款问题",0.96
  ```

  ------

  ## 3. 置信度阈值

  不要所有预测都直接自动处理。

  可以设置规则：

  ```text
  confidence >= 0.90：自动处理
  0.60 <= confidence < 0.90：进入人工复核
  confidence < 0.60：返回兜底标签或转人工
  ```

  ------

  ## 4. 线上推理验收

  上线前至少检查：

  ```text
  - 典型样本是否预测正确
  - 边界样本是否稳定
  - 长文本是否截断严重
  - 空文本、乱码、emoji 是否崩溃
  - 未见过的新表达是否还能合理处理
  - 批量推理速度是否满足业务要求
  ```

  ------

  # 第六阶段：成功判断标准

  满足以下 3 条即可认为一次微调基本成功：

  1. 核心指标比基线提升
  2. 多次训练结果波动小
  3. 典型样本预测正确
  4. 线上或模拟线上样本无明显崩坏
  5. 少数类指标没有明显恶化
  6. 推理速度和显存成本可接受

  更严格的标准：

  ```text
  - 验证集和测试集指标接近
  - Macro F1、关键类别 Recall 达标
  - 错误样本可解释
  - 人工抽检通过
  - 灰度上线表现稳定
  ```

  ------

  # 第七阶段：新手最容易忽略的基础点

  ## 1. 标签必须来自真实标签列

  错误：

  ```text
  从 text、title、category_name 等输入字段复制标签。
  ```

  正确：

  ```text
  从人工标注列、业务结果列或审核后的 label 列读取标签。
  ```

  ------

  ## 2. 训练集和验证集必须严格分开

  错误：

  ```text
  先 tokenize 再随意切分，导致重复样本泄漏。
  ```

  正确：

  ```text
  先去重、清洗、切分，再分别 tokenize。
  ```

  ------

  ## 3. 评估指标需组合使用

  错误：

  ```text
  只看 Accuracy。
  ```

  正确：

  ```text
  同时看 Accuracy、Precision、Recall、F1、混淆矩阵。
  ```

  ------

  ## 4. 不要用测试集调参

  测试集只能在最后使用。

  错误：

  ```text
  每次调完参数都在 test 上看效果。
  ```

  后果：

  ```text
  测试集被间接污染，最终指标不可信。
  ```

  ------

  ## 5. 不要盲目增加 epoch

  epoch 越多不一定越好。

  常见现象：

  ```text
  训练 loss 继续下降，验证 F1 开始下降。
  ```

  这通常说明过拟合。

  ------

  ## 6. 不要忽略线上数据分布

  训练数据如果和线上输入差异太大，模型上线会掉点。

  例如：

  ```text
  训练数据是人工整理后的标准句子；
  线上数据是错别字、口语、emoji、长句、上下文缺失。
  ```

  解决方式：

  ```text
  训练集中加入真实线上样本。
  ```

  ------

  # 第八阶段：常见问题与排查

  ## 1. 显存不足 OOM

  解决方法：

  ```text
  - 降低 batch size
  - 缩短 max_length
  - 使用 gradient_accumulation_steps
  - 使用 fp16 或 bf16
  - 使用 LoRA 或 QLoRA
  - 换更小模型
  - 开启 gradient checkpointing
  ```

  ------

  ## 2. 列名报错

  常见原因：

  ```text
  代码里写的是 text，但数据里叫 content。
  代码里写的是 label，但数据里叫 category。
  ```

  解决方法：

  ```text
  统一列名。
  ```

  推荐标准列名：

  分类任务：

  ```text
  text, label
  ```

  指令微调：

  ```text
  instruction, input, output
  ```

  对话微调：

  ```text
  messages
  ```

  ------

  ## 3. dtype 不兼容

  解决方法：

  ```python
  torch_dtype="auto"
  ```

  或者根据硬件选择：

  ```python
  torch_dtype=torch.float16
  ```

  支持 bf16 的 GPU 可使用：

  ```python
  torch_dtype=torch.bfloat16
  ```

  ------

  ## 4. Loss 不下降

  可能原因：

  ```text
  - labels 设置错误
  - 学习率过低或过高
  - 数据标签混乱
  - prompt 模板不合理
  - 模型类型和任务不匹配
  - tokenizer 截断了关键信息
  ```

  排查顺序：

  ```text
  先检查 labels，再检查数据，再检查学习率。
  ```

  ------

  ## 5. 训练集好，验证集差

  可能原因：

  ```text
  - 过拟合
  - 训练集和验证集分布不同
  - 训练样本太少
  - 标签噪声高
  - 重复样本过多
  ```

  解决方法：

  ```text
  - 减少 epoch
  - 清洗数据
  - 增加验证集覆盖
  - 增加 dropout
  - 增加 weight_decay
  - 使用 early stopping
  ```

  ------

  ## 6. Accuracy 很高，但业务效果差

  可能原因：

  ```text
  类别严重不平衡。
  ```

  例如：

  ```text
  90% 样本都是“正常”，模型全部预测“正常”，Accuracy 也有 90%。
  ```

  解决方法：

  ```text
  - 查看每个类别 Precision、Recall、F1
  - 使用 Macro F1
  - 增加少数类样本
  - 调整采样策略或类别权重
  ```

  ------

  ## 7. 生成任务答非所问

  可能原因：

  ```text
  - 指令格式不统一
  - output 质量差
  - prompt 和线上格式不一致
  - 训练样本太少
  - 学到了错误风格
  ```

  解决方法：

  ```text
  - 统一 instruction 模板
  - 清洗低质量回答
  - 增加高质量示例
  - 上线 prompt 与训练 prompt 保持一致
  ```

  # 第十阶段：推荐最小可行方案

  新手可以先按以下配置跑通第一版：

  ```text
  任务：文本分类
  数据：至少每类 100 条起步，越多越好
  模型：选择一个较小的中文或多语种模型
  微调方式：LoRA
  learning_rate：5e-5
  epoch：3
  batch_size：按显存设置
  max_length：256
  评估指标：Accuracy + Macro F1 + 每类 Recall
  验收方式：验证集指标 + 30 条人工样本测试
  ```

  如果是指令微调：

  ```text
  数据：高质量 instruction/input/output
  模型：Chat/Instruct 版本模型
  微调方式：LoRA 或 QLoRA
  epoch：1–3 起步
  学习率：1e-5 到 2e-4 之间试验
  评估：人工评测 + 自动指标 + 线上模拟样本
  ```

  # 第十一阶段：上线前检查清单

  ## 数据检查

  - 标签是否真实可靠
  - 是否去重
  - 是否有训练/验证泄漏
  - 类别是否严重不平衡
  - 是否覆盖真实线上表达
  - 是否有脏数据和异常样本

  ## 训练检查

  - loss 是否正常下降
  - 是否出现 NaN
  - 是否保存最佳模型
  - 是否固定随机种子
  - 是否记录实验配置
  - 是否能复现结果

  ## 评估检查

  - 是否看了 Accuracy、Precision、Recall、F1
  - 是否看了混淆矩阵
  - 是否和基线比较
  - 是否分析错误样本
  - 是否关注关键类别
  - 是否单独测试边界样本

  ## 推理检查

  - 单条预测是否正确
  - 批量预测是否稳定
  - 低置信度样本是否兜底
  - 空输入、超长输入是否处理
  - 输出格式是否稳定
  - 推理速度是否满足业务要求

  ## 上线检查

  - 是否灰度发布
  - 是否保留回滚方案
  - 是否监控线上指标
  - 是否收集错例
  - 是否建立持续迭代数据闭环

  ------

  # 第十二阶段：完整闭环总结

  微调大模型不是单纯执行训练代码，而是一个完整工程闭环：

  ```text
  明确任务
  → 清洗数据
  → 定义标签
  → 切分数据
  → 跑通训练
  → 评估指标
  → 错误分析
  → 参数调优
  → 推理验收
  → 灰度上线
  → 收集错例
  → 继续迭代
  ```

  最重要的原则：

  ```text
  数据质量优先于参数技巧。
  验证集必须独立。
  标签必须真实。
  指标必须组合看。
  Loss 只能辅助判断训练状态，不能单独代表业务效果。
  推理结果必须用真实样本验收。
  ```

  对于新手，最推荐的路线是：

  ```text
  先用小模型 + 小数据 + LoRA 跑通全流程；
  再清洗数据、补充样本、分析错例；
  最后才系统调参和扩大模型规模。
  ```
