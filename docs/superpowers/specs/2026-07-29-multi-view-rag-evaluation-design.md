# Multi-View Papers RAG Evaluation Pipeline Design

Date: 2026-07-29

## Goal

Build a two-layer evaluation pipeline to measure the RAG Q&A quality for 6 multi-view clustering papers in the knowledge base. Layer 1 evaluates retrieval quality (Recall, Precision, MRR, NDCG, latency). Layer 2 evaluates end-to-end answer quality via LLM-as-Judge (faithfulness, relevance, completeness) plus token consumption and latency. Output a comprehensive Markdown report with actionable insights.

## Current Context

Prism already has evaluation infrastructure:

- **Data models**: `EvaluationDataset` / `EvaluationDatasetItem` / `EvaluationRun` / `EvaluationRunItem` with MySQL persistence and REST API.
- **Engine library**: `engine/app/evaluation/runner.py` (`run_evaluation`, `EvaluationItem`, `EvaluationResult`) and `metrics.py` (`retrieval_metrics` — Recall@K, MRR, NDCG).
- **Offline CLI**: `engine/eval/generate_queries.py` (LLM-generated golden dataset from parent chunks) and `engine/eval/run_retrieval.py` (hybrid search benchmark against golden dataset).
- **Async evaluation job**: `engine/app/jobs/evaluation_handlers.py` (`handle_evaluation`) — worker-driven retrieval evaluation via `execute_retrieval`.

These existing pieces are **retrieval-only** and integrated into the product (API + jobs). The new pipeline needs to be a **standalone CLI** that adds:

1. End-to-end chat/answer evaluation (agent loop → answer generation).
2. Token tracking and latency measurement.
3. LLM-as-Judge answer quality scoring.
4. Cross-paper comparison and grouped analysis.
5. Depth-focused dataset generation (80+ questions with diverse types).

## Product Decisions

1. Questions are 100% in Chinese, generated by LLM from sampled parent chunks.
2. Dataset includes 5 question types: fact lookup, concept explanation, method comparison, data detail, cross-paper comparison.
3. Gold chunks are auto-labeled by LLM from child chunks with 3 relevance tiers: `direct`, `partial`, `context`.
4. Retrieval layer is evaluated first; results feed into end-to-end answer evaluation (shared golden dataset).
5. Answer quality is scored by LLM-as-Judge on 3 dimensions: faithfulness, relevance, completeness.
6. Cross-paper questions reference chunks from 2-3 different papers.
7. All intermediate results are persisted to disk; each step is independently re-runnable.
8. Output format is backward-compatible with existing `golden_dataset.json` so `run_retrieval.py` still works.

### Step Pipeline

```
Step 1: generate_queries_v2.py
  Input:  MySQL (knowledge_item + knowledge_chunk for 6 papers)
  Output: golden_dataset_v2.json (85 questions with gold chunks)

Step 2: run_retrieval_v2.py
  Input:  golden_dataset_v2.json
  Action: call scoped_text_hybrid_search per query
  Output: retrieval_detailed.csv + retrieval_summary.json
         (Recall@K, Precision@K, MRR, NDCG, latency, channel health)

Step 3: run_answer_eval.py
  Input:  golden_dataset_v2.json
  Action: call chat/answer streaming endpoint per query
          → collect answer + sources + tokens + latency
          → LLM-as-Judge scoring
  Output: answer_detailed.csv + answer_summary.json + bad_cases/

Step 4: generate_report.py
  Input:  retrieval_summary.json + answer_summary.json
  Action: cross-reference both layers, compute correlations
  Output: REPORT.md
```

Each step reads its input and writes its output independently. Step 3 can be re-run without re-running Step 2.

## Step 1: Dataset Generation

### Sampling Strategy

- Target: ~85 questions across 6 papers.
- Stratified sampling: ~14 questions per paper (proportional to parent chunk count).
- Within each paper, randomly sample parent chunks; each selected parent generates 1 question.
- Cross-paper questions (~13): pick semantically related parent chunks from 2-3 papers, generate comparison questions.

### Question Type Distribution

| Type | Code | Count | Description |
|------|------|-------|-------------|
| 事实查询 | `fact` | 34 | Specific factual questions answerable from the chunk |
| 概念解释 | `concept` | 17 | Explain a concept or method introduced in the chunk |
| 方法对比 | `method_compare` | 13 | Compare methods/approaches within or across papers |
| 数据细节 | `data_detail` | 8 | Questions about experimental data, metrics, parameters |
| 跨论文对比 | `cross_paper` | 13 | Compare approaches/claims across different papers |

### Generation Prompt Template

Each parent chunk goes through a two-stage LLM pipeline:

**Stage 1 — Question Generation:**

```
你是一个检索质量评估数据生成器。给定一段学术论文内容，请生成一个能用该文档回答的问题。

要求：
- 生成一个自然的中文提问
- 问题类型：{question_type_description}
- 问题答案必须能在这段文档中找到
- 问题长度适中（10-50字）
- 只输出问题本身，不要解释，不要添加前缀

论文：{paper_title}
文档内容：
{chunk_text[:3000]}

问题：
```

**Stage 2 — Gold Chunk Labeling:**

```
你是一个检索评估标注器。给定一个问题和一组候选文本片段，请标注哪些片段包含答案。

问题：{question}
父块内容：{parent_chunk_text[:3000]}

候选子块：
{child_chunks_enumerated}

请判断每个子块的相关性：
- "direct": 直接包含答案的关键信息
- "partial": 包含部分答案或背景信息
- "context": 只提供上下文，不直接回答问题

输出 JSON 数组：{"chunk_id": "...", "relevance": "direct|partial|context"}
只输出 JSON，不要解释。
```

## Step 2: Retrieval Evaluation

### Metrics Per Query

| Metric | Formula / Source |
|--------|------------------|
| `recall@K` (K=5,10,20) | \|retrieved ∩ gold\| / \|gold\| |
| `precision@K` (K=5,10,20) | \|retrieved ∩ gold\| / K |
| `hit@K` (K=5,10,20) | 1 if any hit, else 0 |
| `ndcg@K` (K=10,20) | DCG / IDCG with binary relevance |
| `mrr` | 1 / rank_of_first_hit |
| `first_relevant_rank` | 1-based rank of first gold chunk |
| `latency_ms` | Wall-clock time for the search call |
| `dense_hits` | Number of candidates from Milvus vector channel |
| `bm25_hits` | Number of candidates from ES BM25 channel |
| `graph_hits` | Number of candidates from graph expansion |
| `rerank_applied` | Whether cross-encoder rerank was used |

### Aggregation Dimensions

Group the per-query metrics by:

1. **Paper** — which paper's retrieval quality is best/worst
2. **Question type** — which question types are hardest for retrieval
3. **Paper size** — correlation between document size and retrieval quality
4. **Channel contribution** — how much each channel (dense/BM25/graph) contributes

### Output

```csv
# retrieval_detailed.csv
query_id,question,question_type,paper_title,relevant_count,
recall@5,recall@10,recall@20,precision@5,precision@10,precision@20,

latency_ms,dense_hits,bm25_hits,graph_hits,rerank_applied,
retrieved_detail
```

## Step 3: End-to-End Answer Evaluation

### Agent Invocation

For each query in the dataset, call the Engine chat/answer endpoint (streaming NDJSON):

```python
POST /api/v1/chat/answer
{
  "query": "交互学习机制是如何工作的？",
  "kb_uids": ["9141b989-..."],
  "mode": "standard",       # standard for most; deep for cross_paper
  "history": []
}
```

Parse the NDJSON stream to collect:

- Final `done` event → answer text
- `sources` event → cited chunks with `chunk_uid`, `excerpt`, `file_uid`
- `token` events → cumulative token counts (prompt + completion)
- Timing: TTFB (time to first byte) + total duration

### Metrics Per Query

| Metric | Source |
|--------|--------|
| `answer` | Final answer text from `done` event |
| `source_chunk_uids` | Chunk UIDs from `sources` event |
| `source_count` | Number of cited sources |
| `prompt_tokens` | Total prompt tokens across the agent loop |
| `completion_tokens` | Total completion tokens across the agent loop |
| `total_tokens` | prompt + completion |
| `ttfb_ms` | Time from request to first NDJSON line |
| `total_latency_ms` | Total stream duration |
| `tool_calls` | Number of `knowledge_search` tool invocations |
| `iterations` | Number of agent loop iterations |
| `judge_faithfulness` | LLM judge score (1-5) |
| `judge_relevance` | LLM judge score (1-5) |
| `judge_completeness` | LLM judge score (1-5) |
| `judge_overall` | Weighted average |
| `judge_rationale` | Judge's reasoning text |

### LLM-as-Judge

Use a separate LLM call (can be the same model or a cheaper one) with a structured prompt:

```
你是一个 RAG 问答质量评估器。请严格评估以下回答的质量。

## 问题
{question}

## 参考答案依据（来自知识库的相关片段）
{gold_chunks_text}

## 模型回答
{answer}

## 评估维度（1-5 分，整数）

1. **忠实度 (faithfulness)**：回答是否严格基于提供的知识库内容？
   - 5=完全基于知识库，无任何编造
   - 3=基本基于知识库，有少量不准确
   - 1=大量编造、幻觉，或与知识库矛盾

2. **相关性 (relevance)**：回答是否直接、精确地回应了问题？
   - 5=完全切题，直接回应
   - 3=部分相关，有偏题但大致方向对
   - 1=答非所问

3. **完整性 (completeness)**：回答是否覆盖了知识库中含有的关键要点？
   - 5=覆盖全部关键要点
   - 3=覆盖主要内容，遗漏次要信息
   - 1=遗漏大量关键信息

## 输出格式
只输出 JSON，不要解释：
{"faithfulness": <1-5>, "relevance": <1-5>, "completeness": <1-5>, "rationale": "<一句话理由>"}
```

### Token Tracking

Token counts come from two sources:

1. **LLM API response** (`usage.prompt_tokens` / `usage.completion_tokens`) — aggregated across all LLM calls in the agent loop.
2. **Agent loop instrumentation** — count tool-call LLM rounds separately from final generation.

Track:

```python
token_breakdown = {
    "total_prompt_tokens": sum,      # All prompt tokens across the loop
    "total_completion_tokens": sum,  # All completion tokens across the loop
    "retrieval_llm_tokens": sum,     # Tokens consumed by tool-calling turns
    "generation_tokens": sum,        # Tokens for final answer generation
    "judge_tokens": sum,             # Tokens consumed by LLM judge
}
```

### Bad Case Collection

Any query where `judge_faithfulness < 3` OR `judge_relevance < 3` is flagged. For each flagged query, dump a detailed case file:

```markdown
# Bad Case: q023

**Question:** ...
**Paper:** ...
**Type:** cross_paper

## Answer
...

## Judge Scores
- Faithfulness: 2
- Relevance: 4
- Completeness: 3
- Rationale: "模型声称的方法参数与原始论文矛盾"

## Source Chunks Cited
- [chunk_a] "..." (correct info)
- [chunk_b] "..." (contradicts the answer)

## Gold Chunks (what should have been cited)
- [gold_1] "..."

## Analysis
模型错误地将论文A的方法描述套用到了论文B上，属于跨论文混淆。
```

### Output

```
answer_detailed.csv       — one row per query, all metrics + judge scores
answer_summary.json       — aggregated scores by dimension, type, paper
answer_low_scores.csv     — only flagged queries with low scores
bad_cases/q*.md           — detailed analysis for each flagged case
```

### Generation Approach

`generate_report.py` reads `retrieval_summary.json` + `answer_summary.json` + `answer_detailed.csv`, computes cross-layer correlations, and renders the Markdown report using Python string templates. No external charting library — use ASCII tables for quantitative data and descriptive text for trends.

## Edge Cases & Error Handling

1. **LLM generation failure**: A parent chunk that fails to generate a question is skipped; the sampling quota is filled from remaining chunks.
2. **Retrieval timeout**: Queries exceeding 30s are marked as `timeout` with partial results if any.
3. **Empty retrieval results**: Recorded as `recall=0` with all zero metrics; included in zero-recall analysis.
4. **Agent tool call failure**: If `knowledge_search` tool fails, the agent may fall back to no-tool answering; this is flagged as a special case in answer evaluation.
5. **LLM Judge failure**: If the judge LLM call fails, the query is marked `judge_error` and excluded from judge aggregates but still included in other metrics.
6. **Streaming interruption**: If the chat stream is interrupted, partial answer text is still evaluated with a `stream_incomplete` flag.
7. **Cross-paper gold chunks**: Cross-paper questions have `paper_ids: [...]` array and `relevant_children` spans multiple papers' chunks. The retrieval eval uses all gold chunk IDs regardless of paper source.

## Key Constraints

1. No modification to existing production evaluation API or models — this is a standalone CLI toolset.
2. Backward-compatible dataset format — v2 datasets work with existing `run_retrieval.py`.
3. All LLM calls (generation, judging) use the project's existing `engine/app/llm/client.py` for consistency.
4. Database access is read-only — only queries, no writes.
5. Results directory must support multiple runs without overwriting (timestamped directories).
