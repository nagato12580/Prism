# TopicGroup Semantic Clustering Design

## Goal

Introduce semantic topic grouping for Prism's knowledge graph without using CKP parent nodes as classification directories.

The target product flow is:

```text
Automatically generate TopicGroup drafts -> user reviews and edits -> confirmed TopicGroups are projected to Neo4j
```

CKP remains an atomic knowledge point. TopicGroup becomes the reviewable grouping, clustering, and browsing layer.

This design also keeps entity disambiguation in the Entity/Alias layer. TopicGroup clustering groups knowledge points; it does not decide whether two names refer to the same real-world entity.

## Current Problem

The current CKP governance flow creates two kinds of CKP records:

- Child CKP: atomic topics such as "DPO", "PPO", "LoRA", or "Python import rules".
- Parent CKP: generated rollups such as "optimization and experimental validation" or "X and Y".

After projecting to Neo4j, both appear as `(:CKP)` nodes. This makes the graph hard to read because some CKP nodes are real knowledge points while others are directory-like labels.

Neo4j makes a separate grouping layer more natural. Grouping can be expressed with graph relationships instead of forcing CKP into a tree.

## Design Principles

- MySQL remains the source of truth.
- Neo4j remains a derived projection and graph index.
- CKP is an atomic knowledge point, not a folder or category.
- TopicGroup is a grouping, cluster, or curated view over CKP.
- Automatic clustering creates drafts first; user confirmation promotes drafts to formal groups.
- A CKP may belong to multiple TopicGroups.
- TopicGroups may be recalculated without rewriting CKP identity.
- Confirmed user edits must survive future automatic clustering.

## Conceptual Model

```text
TopicGroupDraft
  -> candidate group generated by clustering and LLM labeling

TopicGroup
  -> confirmed group after user review

TopicGroupMember
  -> membership edge from TopicGroup to CKP

CKP
  -> atomic knowledge point

PKU
  -> evidence unit supporting CKP

Source
  -> source document, chunk, asset item, or asset unit

Entity
  -> concrete named object such as person, paper, organization, email, project

EntityResolutionCandidate
  -> reviewable suggestion that an alias or mention should resolve to an existing Entity
```

Target graph shape:

```text
(:TopicGroup {name: "强化学习算法"})
  -[:CONTAINS {confidence, reason, rank}]->
(:CKP {title: "DPO"})
  -[:SUPPORTED_BY]->
(:PKU)
  -[:EVIDENCED_BY]->
(:Source)

(:Entity)-[:MENTIONED_IN]->(:Source)
(:CKP)-[:RELATED_TO]->(:CKP)
```

Entity disambiguation graph shape:

```text
(:Alias {surface_text: "谭彦超", key: "谭彦超"})
  -[:ALIAS_OF {confidence, evidence_summary}]->
(:Entity {canonical_name: "Yanchao Tan", entity_type: "person"})

(:Alias {surface_text: "yanchaotan", key: "yanchaotan"})
  -[:ALIAS_OF]->
(:Entity {canonical_name: "Yanchao Tan", entity_type: "person"})
```

## Data Model

### `topic_group_draft`

Stores generated group candidates before user confirmation.

Fields:

- `id`
- `user_id`
- `name`
- `description`
- `group_type`: initially `semantic_cluster`
- `algorithm`: for example `embedding_threshold_v1`
- `status`: `pending_review`, `confirmed`, `rejected`, `superseded`
- `confidence`
- `reason`
- `keywords`
- `metadata`
- `created_at`
- `updated_at`

Draft metadata should include:

- clustering parameters
- source CKP ids
- LLM model used for naming
- generation run id

### `topic_group_draft_member`

Stores candidate CKP membership for drafts.

Fields:

- `id`
- `draft_id`
- `ckp_id`
- `confidence`
- `reason`
- `rank`
- `created_at`

### `topic_group`

Stores confirmed groups.

Fields:

- `id`
- `user_id`
- `name`
- `description`
- `group_type`: `semantic_cluster`, later `manual`, `source`, `entity`
- `origin_draft_id`
- `status`: `active`, `archived`
- `confidence`
- `keywords`
- `metadata`
- `created_at`
- `updated_at`

Confirmed group metadata should include user edits:

- original generated name
- original generated description
- reviewer id if available
- confirmed timestamp
- generation run id

### `topic_group_member`

Stores confirmed membership from TopicGroup to CKP.

Fields:

- `id`
- `group_id`
- `ckp_id`
- `confidence`
- `reason`
- `rank`
- `source`: `generated`, `user_added`, `user_removed_restore`
- `created_at`
- `updated_at`

Uniqueness:

- one active membership per `(group_id, ckp_id)`.

### `entity_resolution_candidate`

Stores candidate alias/entity merges before user confirmation. This is the layer that can resolve cases such as `yanchaotan`, `Yanchao Tan`, and `谭彦超` to one canonical Entity.

Fields:

- `id`
- `user_id`
- `alias_surface`
- `alias_normalized_key`
- `candidate_entity_id`
- `candidate_entity_name`
- `entity_type`
- `confidence`
- `status`: `pending_review`, `confirmed`, `rejected`, `superseded`
- `evidence_summary`
- `evidence`
- `resolution_method`: `rule`, `llm`, `graph_evidence`, `user_confirmed`
- `created_at`
- `updated_at`

Evidence should be JSON and may include:

- shared source ids
- shared paper title
- shared email
- shared affiliation
- shared coauthor list
- co-mentioned entities
- LLM explanation

Confirmation creates or updates `EntityAlias` so the alias points to the canonical `KnowledgeEntity`.

## Clustering Flow

### 1. Select CKP Candidates

Only cluster atomic CKP records.

Initial selector:

```text
CanonicalKnowledgePoint.user_id == user_id
CanonicalKnowledgePoint.status != "deprecated"
CanonicalKnowledgePoint.canonical_type == "topic"
extra_meta.topic_level != "parent"
```

If `topic_level` is missing, treat the CKP as atomic unless future migration marks it otherwise.

### 2. Build Semantic Text

Each CKP gets a clustering text assembled from:

- `title`
- `canonical_statement`
- `summary`
- `keywords`
- `concepts`
- `entities`
- linked PKU statements
- source titles from linked PKU

Example:

```text
Title: DPO
Statement: Direct Preference Optimization optimizes language model behavior from preference pairs without explicit reward model training.
Keywords: preference optimization, RLHF, policy optimization
Related PKU: ...
```

### 3. Embed CKP Text

Reuse Prism's existing embedding provider where possible.

The first version can run as an offline script or backend service job. It should not require real-time user interaction.

### 4. Cluster CKP

Initial algorithm:

- cosine similarity over CKP embeddings
- threshold-based agglomeration
- minimum group size of 2
- maximum group size cap to keep review manageable

For example, DPO, PPO, GRPO, and RLHF-related CKP should cluster into a candidate group.

### 5. Label With LLM

For each cluster, ask the LLM to produce:

```json
{
  "name": "强化学习算法",
  "description": "包含用于策略优化、偏好优化和强化学习对齐的算法与方法。",
  "keywords": ["PPO", "DPO", "GRPO", "RLHF", "策略优化"],
  "confidence": 0.86,
  "reason": "这些知识点都围绕强化学习或偏好优化算法。"
}
```

The LLM labels the group. It does not rewrite CKP.

### 6. Create Drafts

Persist `TopicGroupDraft` and `TopicGroupDraftMember` rows with `pending_review`.

The generator must avoid duplicate open drafts for the same near-identical CKP member set.

### 7. Review and Confirm

The user can:

- confirm a draft
- rename it
- edit description
- remove members
- add members
- reject it
- merge drafts
- split a draft later

Confirmation creates a `TopicGroup` and `TopicGroupMember` rows.

### 8. Project to Neo4j

Confirmed groups project to Neo4j:

```text
(:TopicGroup {
  id,
  user_id,
  name,
  description,
  group_type,
  status,
  confidence
})

(:TopicGroup)-[:CONTAINS {
  confidence,
  reason,
  rank,
  source
}]->(:CKP)
```

Drafts are not projected by default. A debug option may project drafts with label `TopicGroupDraft`, but that should not be used in the main graph view.

## Entity Disambiguation Flow

TopicGroup semantic clustering and entity disambiguation are adjacent but separate workflows.

TopicGroup answers:

```text
Which CKP belong together as a semantic group?
```

Entity disambiguation answers:

```text
Do these aliases or mentions refer to the same real-world entity?
```

### 1. Extract Mentions

Entity extraction creates `KnowledgeEntity`, `EntityMention`, and `EntityAlias` rows from source text.

Examples:

```text
Yanchao Tan
yanchaotan
Tan Yanchao
谭彦超
yctan@fzu.edu.cn
Fuzhou University
OpenViewer
```

### 2. Generate Alias Candidates

Rules can safely generate deterministic aliases for the same script:

- lowercased compact Latin names
- given-family and family-given Latin order
- email local-part hints

Rules should not automatically merge cross-language names such as `谭彦超 -> Yanchao Tan` unless there is strong supporting evidence.

### 3. Score Cross-Language Resolution Candidates

For cases such as `谭彦超` and `Yanchao Tan`, create `EntityResolutionCandidate` rows instead of directly merging.

Signals:

- same source or same document chunk
- same paper title
- same email address or email local-part hint
- same affiliation
- overlapping coauthor names
- graph proximity in Neo4j
- LLM judgment with cited evidence

High confidence candidates may be auto-confirmed only when deterministic evidence is strong, such as the same email or an explicitly bilingual name line. Otherwise they remain pending review.

### 4. Review and Confirm

The user can:

- confirm alias merge
- reject alias merge
- choose a different canonical Entity
- create a new Entity

Confirming `谭彦超 -> Yanchao Tan` creates:

```text
EntityAlias(alias="谭彦超", normalized_key="谭彦超", entity_id=<Yanchao Tan entity id>)
```

Neo4j projection then emits:

```text
(:Alias {surface_text: "谭彦超"})
  -[:ALIAS_OF]->
(:Entity {canonical_name: "Yanchao Tan"})
```

### 5. Query Behavior

`entity_graph_search` should resolve through aliases before declaring a named entity missing.

Search order:

1. exact alias key
2. normalized Latin alias variants
3. confirmed cross-language aliases
4. pending candidates surfaced as "possible matches" if no confirmed match exists

For `yanchaotan` or `谭彦超`, the desired result is the same canonical Entity once the alias is confirmed.

## Product Behavior

Default graph browsing should prioritize:

```text
TopicGroup -> CKP -> PKU -> Source
```

For a group such as "强化学习算法", the user should see CKP members like:

- DPO
- PPO
- GRPO
- RLHF
- reward model
- preference optimization

Selecting a CKP then shows supporting PKU, source evidence, and related entities.

Entity review should be a separate review surface from TopicGroup review:

```text
Possible alias: 谭彦超
Candidate entity: Yanchao Tan
Evidence: same paper "OpenViewer", same affiliation "Fuzhou University", coauthor overlap
Action: confirm / reject / create new entity
```

Confirmed entity aliases immediately improve graph search and entity-centric retrieval.

## CKP Parent Node Policy

Parent CKP generation should be deprecated for the Neo4j-centered architecture.

Short-term:

- keep existing parent CKP rows in MySQL for compatibility
- do not show parent CKP as primary graph nodes
- project `topic_level` into Neo4j so parent and child CKP can be filtered

Medium-term:

- stop creating new parent CKP in `_settle_local_pku_topics`
- stop creating `subtopic_of` relations as the main grouping mechanism
- replace that behavior with TopicGroupDraft generation

Long-term:

- treat existing parent CKP as migration candidates
- convert high-quality parent CKP into TopicGroup drafts where useful
- archive or hide low-quality parent CKP

## Error Handling

Clustering should be best-effort.

- If embedding fails for a CKP, skip it and record the error in the generation run metadata.
- If LLM labeling fails for a cluster, create a draft with a deterministic fallback name such as the highest ranked CKP title plus "相关主题".
- If confirmation races with regeneration, keep confirmed groups and mark conflicting drafts as `superseded`.
- If projection to Neo4j fails, leave MySQL confirmed groups intact and retry projection later.
- If entity resolution confidence is ambiguous, create a pending candidate instead of merging.
- If a user rejects a candidate, future generation should not recreate the same candidate unless new stronger evidence appears.
- If two confirmed entities are later found to be the same person, merge through an explicit user-confirmed operation that preserves old aliases and mentions.

## Testing Strategy

Unit tests:

- CKP selector excludes `topic_level == "parent"`.
- Semantic text builder includes title, statement, keywords, concepts, entities, PKU statements, and source titles.
- Clustering groups similar CKP and leaves unrelated CKP separate using deterministic fake embeddings.
- LLM label parser accepts valid labels and rejects empty group names.
- Draft deduplication avoids duplicate pending drafts for the same member set.
- Confirming a draft creates one TopicGroup and expected members.
- Neo4j projection emits `TopicGroup` nodes and `CONTAINS` relationships.
- Entity resolution candidate generation creates a pending candidate for cross-language aliases with shared evidence.
- Confirming an entity resolution candidate creates an `EntityAlias` pointing to the canonical entity.
- `entity_graph_search` resolves a confirmed alias such as `谭彦超` to the same entity as `Yanchao Tan`.

Integration tests:

- Seed CKP for DPO, PPO, GRPO, and unrelated "Python import rules"; verify the first three produce one draft group and the unrelated CKP does not join it.
- Confirm the draft and project it into FakeGraph.
- Seed mentions for `Yanchao Tan`, `谭彦超`, `OpenViewer`, and `Fuzhou University`; verify the resolver creates a candidate rather than direct auto-merge when evidence is suggestive but not deterministic.
- Confirm the candidate and verify Neo4j has one Entity with both aliases.

Manual smoke:

- Run generator against the real MySQL database.
- Confirm one generated group.
- Project to Neo4j.
- In Neo4j Browser, verify:

```cypher
MATCH p=(:TopicGroup {name: "强化学习算法"})-[:CONTAINS]->(:CKP)
RETURN p
```

## Open Decisions

The initial implementation should choose conservative defaults:

- minimum group size: 2
- max group size: 20
- similarity threshold: start around 0.78 and tune from real data
- only cluster `canonical_type == "topic"` first
- drafts are not projected to Neo4j by default

Future iterations can add manual groups, entity-centric groups, source-based groups, and graph community detection.

Entity disambiguation defaults:

- deterministic same-script aliases can auto-link
- cross-language aliases start as pending candidates unless email or explicit bilingual evidence is present
- rejected candidates are remembered
- confirmed aliases are projected to Neo4j and used by `entity_graph_search`
