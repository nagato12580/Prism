## MVCC（多版本并发控制）

MVCC（Multi-Version Concurrency Control，多版本并发控制）是一种数据库并发控制机制，核心思路是**让读操作不阻塞写操作，写操作也不阻塞读操作**，从而大幅提升并发性能。

### 核心思想

- 每次对数据的修改，不是直接覆盖旧值，而是**生成一个新版本**，旧版本保留。
- 不同的事务看到的是数据在某个时间点的**快照**，而不是实时最新值。
- 通过维护多个版本来实现读写分离，互不干扰。

### 典型实现方式

以 InnoDB（MySQL）为例，MVCC 依赖三个关键机制：

| 机制 | 说明 |
|------|------|
| **隐藏字段** | 每行记录额外保存 `DB_TRX_ID`（最后修改该行的事务ID）和 `DB_ROLL_PTR`（回滚指针，指向旧版本） |
| **Undo Log** | 记录数据的旧版本，用于构造历史快照 |
| **Read View** | 事务在某个时间点生成的"可见性快照"，决定哪些版本对该事务可见 |

### 工作流程示例

```
时间线：
T1: 开始事务，插入一行 A=1      → 版本 V1
T2: 开始事务
T3: T1 提交
T4: T2 查询 A                 → 看到 A=1（读的是 T2 开始时的快照）
T5: T3 更新 A=2               → 生成新版本 V2，V1 保留在 Undo Log
T6: T2 再次查询 A              → 仍然看到 A=1（基于 T2 的 Read View）
T7: T3 提交
```

T2 事务在整个过程中读到的始终是**事务开始时的那份快照**（取决于隔离级别），不受 T3 修改的影响。

### 解决 & 未解决的问题

**解决的：**
- 读-写冲突不再互斥，读不等待写，写不等待读
- 大幅提升读多写少场景下的并发性能

**未解决的（仍需要锁）：**
- 写-写冲突（两个事务同时修改同一条数据）仍需通过行锁解决
- 幻读问题需要间隙锁（Gap Lock）配合

### 主流数据库中的 MVCC

| 数据库 | MVCC 实现 |
|--------|-----------|
| MySQL / InnoDB | Undo Log + Read View |
| PostgreSQL | 每个元组保存 `xmin`/`xmax` 可见性标记 |
| Oracle | 通过回滚段（Rollback Segment）实现 |
| SQLite (WAL模式) | WAL 文件保留多个版本 |

简单来说，**MVCC 让每个事务透过自己的"快照镜头"看数据，不同事务看到的内容可以不同，从而在不加锁的情况下实现了高效的并发读取。**
